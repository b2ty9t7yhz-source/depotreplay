# Competitive analysis

This review compares DepotReplay with adjacent open-source projects using their public GitHub READMEs and repository metadata as inspected on **2026-08-27**, with DepotReplay's local implementation state updated on **2026-08-28**. It is a product-positioning exercise, not a claim that every feature in another repository was exhaustively audited. “Not documented” below means only that the inspected README did not advertise the capability.

## Comparable projects

| Project | Documented strength | Gap exposed in DepotReplay | Positioning decision |
| --- | --- | --- | --- |
| [GraphHopper jsprit](https://github.com/graphhopper/jsprit) | Java 21 toolkit for rich VRPs, including time windows, multiple depots, heterogeneous fleets, pickups/deliveries, and extension points | DepotReplay supports a deliberately smaller model and only a bounded exact solver | Do not compete on solver breadth. Keep the exact limit explicit and make evaluation easier to inspect and reproduce |
| [PyVRP](https://github.com/PyVRP/PyVRP) | Research-grade solver with rich constraints, tutorials, documented algorithms, and benchmark-oriented workflows | A single hand-authored scenario is weak evidence for comparing heuristics | Provide a deterministic multi-seed challenge suite with machine-readable results and independent regeneration |
| [Google Fleet Routing App](https://github.com/googlemaps/js-route-optimization-app) | Interactive forms, tables, and maps for constructing and tuning route-optimization scenarios | DepotReplay still lacks browser scenario construction; verified replay import/export now covers result sharing | Keep replay verification as the differentiator, then consider a small scenario editor without adding a server or billing dependency |
| [FleetPy](https://github.com/TUM-VT/FleetPy) | Modular, agent-based fleet simulation with demand models, charging, result files, replay, and city data sets | DepotReplay has no dynamic demand, charging, or city-scale claims | Keep the game small and deterministic; add versioned dynamic events only when replay semantics and tests are defined first |
| [VeRoViz](https://github.com/optimatorlab/veroviz) | Road-network data, interactive maps, and dynamic 4D route movies | DepotReplay can step through one baseline at a time but lacks seeking and synchronized player/strategy overlays | Add a tick scrubber and ghost routes before pursuing geographic-map realism |

## Defensible niche

Mature routing libraries already win on constraint breadth, scale, and optimization quality. DepotReplay should instead be the easiest repository in this comparison to use for a small, inspectable counterfactual experiment:

1. **Play it immediately.** The static browser game requires no account, API key, server, or billing setup.
2. **Explain every score.** Player and baseline outcomes expose distance, lateness, unserved work, routes, and completion ticks.
3. **Reproduce every state.** Commands, canonical serialization, per-tick hashes, save reconstruction, and replay verification share one engine.
4. **Check more than one convenient example.** Seed ranges provide repeatable scenario sets instead of a hand-picked screenshot result.
5. **State limits honestly.** The exact solver and synthetic grid model have published boundaries; no production routing performance is implied.

## Improvements implemented from this review

### Deterministic multi-seed benchmark

The `benchmark` command now evaluates every built-in strategy over a consecutive seed range generated by `seeded-grid-v1`. Its canonical JSON report contains:

- the simulation contract and generator versions, seed range, scenario names, and canonical scenario hashes;
- the full score breakdown and final state hash for every strategy/scenario pair;
- integer-only aggregate totals and best-score counts, with every tied strategy counted as best;
- stable strategy and scenario ordering.

The service rejects empty ranges, ranges larger than 1,000 scenarios, and signed 64-bit seed overflow. The limit prevents an accidental unbounded local or CI run; it is not a solver scalability claim.

`verify-benchmark` regenerates the scenarios, reruns all strategies, and compares the complete report. A changed seed, score, aggregate, strategy order, scenario hash, or final state hash fails verification. CI generates and verifies the fixed 25-scenario range `0..24`, then uploads the JSON report as a build artifact.

### In-game baseline review

The browser and desktop game can now load each baseline's deterministic command sequence and step through it one tick at a time. The selected baseline is highlighted while the existing grid, routes, vehicle loads, task timeline, and score decomposition update from the same engine used for player runs. This closes the gap between a static leaderboard and an inspectable counterfactual without introducing a second simulation path.

### Verified browser replay exchange

The static browser build now downloads the same canonical replay format as the CLI, accepts a selected replay file, strictly decodes its schema, and verifies the scenario, command history, every tick hash, and final hash through the shared `ReplayService`. A successful replay starts at tick 0 in the existing renderer; a changed tick hash is rejected before visualization. Browser storage is origin-local, imports are capped at 5 MB before parsing, and no replay data is uploaded.

The Chromium smoke test exercises export, file selection, verification, one-tick visual playback, hash corruption, and the file-size boundary against the generated TeaVM site.

### Why this is more useful than a runtime leaderboard

DepotReplay does not publish solver speed or optimality percentages from this suite. The three baselines are simple, and wall-clock measurements would vary by host. The report instead captures deterministic behavioral evidence that reviewers can regenerate from source.

## Prioritized opportunities

### P0 — Replay seeking and comparison overlays

Build on the verified step-by-step replay viewer with a tick scrubber and synchronized player/baseline ghost routes. Seeking must use already verified states or deterministic reconstruction without changing the verified final hash.

Acceptance criteria:

- seeking backward and forward preserves the verified final hash;
- player and baseline routes share a clearly labeled tick and score frame;
- automated browser tests cover seek boundaries and overlay selection.

### P1 — Browser scenario editor

Provide a grid editor for obstacles, task endpoints, demands, deadlines, capacities, score weights, seed, and path algorithm. Export the existing versioned scenario JSON rather than creating a browser-only format.

Acceptance criteria:

- the same validation rules and messages are used by CLI, desktop, and browser;
- exported JSON passes `validate` and preserves its canonical scenario hash after round-trip;
- keyboard-only operation and touch controls are supported.

### P1 — Strategy extension contract

Turn the internal strategy interface into a documented extension point with a small example strategy and a compatibility test kit. External strategies should receive immutable snapshots and return commands, never mutate engine state.

### P2 — Versioned dynamic requests

Add task release ticks or deterministic incident events only through a new scenario schema version. Replay fixtures must prove compatibility, and the exact solver must either support the new semantics within a revised limit or fail fast with a precise reason.

## Features intentionally not copied

- Real road networks, traffic prediction, and city-scale demand would change the project from a focused game into a research simulator.
- Production-grade metaheuristics would duplicate stronger libraries without improving the replay-verification story.
- Cloud route APIs would remove the zero-account, zero-billing browser experience.
- Unsourced performance or quality claims would conflict with the project's evidence-first goal.
